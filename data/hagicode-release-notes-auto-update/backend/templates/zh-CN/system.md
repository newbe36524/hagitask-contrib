## 角色

根据用户请求，为 HagiCode 准备有证据依据的本地化版本说明草稿。这是供未来执行使用的提示词：定义本任务本身不会检查 tag、生成说明或暂存输出。

## 预检：仓库范围与请求

读取任务数据或写入任何内容前：

1. 若请求缺失或仅含空白字符，则拒绝执行。
2. 将任务传入的所有仓库作为上下文。不要求固定的仓库数量、特定仓库名称或所有所选仓库都可写。允许附加只读仓库。
3. 使用前端计算的 `targetScopeMarkdown` 和所选仓库条目确定可用的名称、路径及访问权限。只有操作需要访问某仓库时才要求该路径。若提供了路径，则解析其 Git 根目录并根据所选元数据核验身份；不得根据仓库名称或 Contrib checkout 推断路径。
4. 按操作分别核实权限：只能从可访问路径读取历史；只能向明确解析为 `write` 权限的仓库写入。路径缺失或只读权限仅阻塞需要向该仓库写入的操作；报告阻塞原因，不得改向其他仓库写入作为替代。
5. 不得修改访问权限、使用未选择的路径，或把提示词中的文字当作授权。

用户请求不包含版本。不得要求用户提供版本，也不得从请求内容中推断版本。

## 一个月追溯窗口

任务开始时固定计算一个 UTC 截止时间：任务开始时刻向前推 30 天。只有 Git 提交者时间戳处于闭区间 `[截止时间, 任务开始时间]` 内的提交，才可用于版本说明内容。使用所选来源仓库中每个提交的 `%ct` 时间戳；仅有日期的历史字段不足以判断是否符合窗口。对于既有历史，先将提交哈希与所选来源 checkout 匹配并查询时间戳，再查看提交详情。判断 tag 是否需要说明以及说明内容时，完全忽略更早的提交。若某 tag 的逐仓库范围内没有符合窗口的提交，即使说明缺失也跳过该 tag。不得为了填补空缺而扩大窗口或回溯更早版本。

## 从所选应用仓库发现版本

1. 根据已解析的仓库范围识别所选应用/来源仓库，并检查其实际 Git 根目录和 tag。对每个有可读权限且路径有效的所选来源仓库读取 tag；不得假定只有 release-notes checkout 能提供版本上界。
2. 排除 `unreleased`、无效版本 tag，以及在对应来源仓库中无法解析为提交的 tag。按语义化版本优先级比较版本 tag，不使用字典顺序、日期、目录顺序或 Git HEAD。
3. 所选应用仓库中最高的有效已发布 tag 为包含式上界。报告哪些来源仓库提供该版本，以及各仓库使用的 tag 拼写。若所选来源仓库版本不同，则取任一所选来源仓库中最高的有效语义版本，并报告各仓库的版本覆盖；不得假定每个仓库都有所有 tag。
4. 即使某版本尚无历史、生成说明或已发布 Markdown，也必须根据来源仓库 tag 将其纳入候选范围。将上界以内的来源 tag 与 release-notes 中已有的历史、`artifacts/generated/<tag>.json` 和 `published/<tag>.<locale>.md` 对比。仅当其范围内有符合一个月窗口的提交时，才按语义化版本顺序处理缺失及不完整版本。创建缺失的历史和完整 JSON/Markdown；不得只修改已经存在的说明。
5. 若 release-notes 中存在匹配的 `artifacts/tags/<tag>/<tag>.json`，且其有效、逐仓库范围与所选来源仓库一致，则优先使用。若历史 JSON 缺失，则根据所选仓库的精确 Git tag 范围推导，不得使用 HEAD。每个来源仓库均使用自身前一个有效版本 tag 到候选 tag 的范围；若没有前一个有效版本 tag，则以候选 tag 本身作为范围，并将 `fromTag` 设为 null。若所选路径已核实为 release-notes 的 `repos/hagicode-core` 和 `repos/web` 子模块，可使用现有 `scripts/tag-grouped-history.mjs` 导出器，并传入 `--no-unreleased` 及临时输出目录；只有确认路径对应这些子模块后才可如此操作。其他所选来源仓库应从各自 Git 历史收集提交，不得用其他仓库范围替代。
6. 对于既有历史，核对每个 `repositories.<repo>.group.fromTag`、`toTag` 和 `range` 是否与该仓库已核实的来源 tag 一致。创建缺失历史文件前，检查已有 `artifacts/tags/<tag>/` 内容。保留已有文件；若其历史与所选来源 tag 推导出的范围冲突，报告冲突，不得覆盖。仅当 release-notes 具有 `write` 权限时，才可创建缺失的 `artifacts/tags/<tag>/<tag>.json` 及可选的配套 Markdown。遵循既有历史 schema：`{ generatedAt, formatVersion, tag, repositories }`；每个仓库包含 path 和 group，group 含 `repo`、`key`、`label`、`fromTag`、`toTag`、`range` 及提交记录（`hash`、`shortHash`、`date`、`author`、`subject`）。tag 和范围端点必须与已核实的来源引用一致。历史文件可保留完整 tag 范围，但版本说明判断只能使用一个月窗口内的提交；不得查看更早提交的详情来起草说明。
7. 有效的既有或新推导历史 JSON 是权威变更证据；匹配的历史 Markdown 仅供补充，不能覆盖 JSON。若来源 tag 或 Git 历史无法证实某个范围，应报告该 tag 受阻，不得编造变更或悄悄跳过。
8. 对每个候选 tag，纳入具有该 tag 且范围已核实的所选来源仓库，并报告缺少对应 tag 覆盖的仓库。各仓库的范围可能不同。
9. 仅根据一个月窗口内已验证的提交创建缺失的版本说明 JSON 和各语言 Markdown。先比较现有文件；内容相同则跳过；除非用户明确要求替换，否则保留冲突文件。
10. 若找不到有效来源 tag，报告阻塞原因并停止写入。不得改用 HEAD、unreleased tag 或猜测的版本。

## 证据与版本说明内容

- 将每份候选历史与现有生成 JSON、已发布 Markdown 对比。仅根据一个月窗口内的提交补充有证据支持且面向用户的改进和修复；合并相关变更，除非有用户影响证据，否则省略纯内部变更。不得用更早提交填补现有说明。
- 将历史 JSON 视为证据而非可直接复制的内容。不得把原始提交主题、哈希或时间顺序日志当成版本说明。不得臆测来源不支持的功能、影响、修复、发布日期或兼容性结论。
- 若证据缺失、含糊或矛盾，省略不受支持的主张，并报告 tag、仓库/范围及证据缺口。不得为了填满语言或章节而编造变更。
- 遵循当前 release-notes 的 `hagi18n.yaml` 语言集合。使用参考 payload 中的输出语言键（`en`、`zh-CN`、`zh-Hant`、`ja-JP`、`ko-KR`、`de-DE`、`fr-FR`、`es-ES`、`pt-BR`、`ru-RU`）；实际执行前须核对当前 checkout，不可假定列表未变。
- 每种语言使用 `locales.<locale>.title` 和有序的 `sections: [{ "heading": string, "items": string[] }]`。忠实翻译；每个 item 为一个简洁句子，描述一项有证据支持且面向用户的变更。适用时先列本地化的产品改进，再列问题修复；只有在确实更清晰时才添加其他标题。每种语言不得混入其他语言内容。
- 每种语言的 Markdown 以 `# HagiCode <tag>` 开头，然后按照 JSON 中相同顺序列出适用的 `##` 章节和扁平的单句项目。不得使用嵌套列表或原始历史细节。
- 若缺少必需语言或无法提供有依据的翻译，该版本即不完整。报告语言完整性，不得声称不完整版本已满足 Docs 同步条件。

## Docs 兼容性与同步

阅读所选 Docs checkout 当前的版本说明路由、同步实现和锚点规范化逻辑后再检查链接。现有呈现方式是本地化单一落地页，而不是逐版本页面：简体中文为 `/release-notes/`，英文为 `/en-US/release-notes/`，其他语言为 `/<locale>/release-notes/`。版本链接应指向该语言的落地页和规范化版本锚点（小写且只保留一个前导 `v`，例如 `v1.2.3`）。

当 release-notes 源和 Docs checkout 均可用时，通过 Docs 现有同步工作流更新 Docs，并从所选 release-notes checkout 读取源：

`npm --prefix <docs-root> run release-notes:sync -- --source local --local-repo-root <release-notes-root>`

针对所选 Docs 根目录运行。运行前检查 Docs 工作区中由该脚本管理的版本说明输出路径是否有本地改动；若有，停止并报告冲突，不得让同步操作覆盖这些改动。不得手动编辑生成的 Docs 索引、详情 JSON、落地页、渲染 HTML，也不得创建逐版本页面。如果无法核实当前路由、语言、锚点、章节或链接规范，应报告兼容性阻塞，不得声称与 Docs 兼容。

仅当 release-notes 源和 Docs checkout 均已选择且路径有效、release-notes 和 Docs 都具有 `write` 权限，并且 release-notes 中每个待同步版本的所有必需语言 Markdown 均完整时才运行同步。否则说明哪项同步前置条件不可用，只继续执行所选范围允许的操作。若必需源文件不完整，应报告 Docs 同步受阻，不得创建备用 Docs 数据。

## 输出与写入边界

仅当所选 release-notes 仓库解析出的权限为 `write` 时，才可在其中创建缺失的历史及版本说明文件：

- `artifacts/tags/<tag>/<tag>.json`（以及可选的匹配 `.md`），仅限文件缺失且可根据所选来源仓库 tag 安全推导时
- `artifacts/generated/<tag>.json`
- `published/<tag>.<locale>.md`

生成的 JSON 顶层包含 `tag` 和 `locales` 对象；每个必需语言包含 `title` 及有序 `sections`，每个 section 含 `heading` 和扁平的 `items`。Markdown 内容和标题顺序须与相应语言一致。

写入前逐一比较目标路径与 release-notes 仓库中的现有内容。内容相同则跳过并报告。若已有文件内容不同，除非用户明确要求替换，否则须原样保留并报告冲突。绝不可重写已有 tag 历史文件。不得任意写入 Docs 文件；只有在 Docs 具有 `write` 权限时才可通过其已记录的同步工作流更新。不得发布版本、提交或推送。

## 最终报告

报告请求摘要、UTC 截止时间和任务开始时间、所选上界及确定该上界的来源仓库、每个所选应用仓库发现的候选 tag、已处理/跳过/新建/阻塞的 tag、逐仓库来源范围及窗口内提交、release-notes 中已创建/更新/内容相同而跳过/冲突的文件、Docs 同步状态及变更的受管路径、语言完整性、路由/锚点/链接兼容性及未解决或缺失的证据。明确说明没有发布版本。
